## 三、边界情况与异常处理

| 编号 | 问题 | 证据 | 影响 | 优先级 |
|---|---|---|---|---|
| E1 | **名称含单引号会截断事件** | 29 处 `onclick="fn('${name}')"` 直接拼接；应用名只校验非空与长度 | 应用名叫 `O'Reilly` 后，该应用所有按钮失效；同时是 HTML 注入入口 | **P0** |
| E2 | **无全局错误边界** | 只有 3 处局部 try/catch；任一视图抛错即白屏 | 演示现场白屏，且没有任何提示 | **P0** |
| E3 | 表单不支持 Enter 提交 | 弹窗无 keydown 监听 | 填完按回车没反应，必须找按钮 | P0 |
| E4 | 弹窗不支持 Esc 关闭 | 同上 | 习惯键盘的人被困住 | P0 |
| E5 | 时间数据是静态字符串 | 告警「13:28」「昨天」，数据写死在 JSON | 隔天演示会显示过期时间，评审会追问 | P1 |
| E6 | 无并发编辑冲突提示 | 两人同改一条配置，后保存的静默覆盖 | 数据被无声吞掉 | P1 |
| E7 | 资源不足无失败态 | 扩容到超过限额不报错，直接显示成功 | 「点了就好」的假象 | P2 |
| E8 | localStorage 不可用时静默降级 | `catch { }` 空处理，用户无感知 | 以为保存成功，刷新后全丢 | P2 |
| E9 | 浏览器后退不保持状态 | hash 路由整页重绘，滚动位置与展开节点丢失 | 从详情返回列表要重新找 | P2 |

## 五、性能与稳定性

| 编号 | 问题 | 当前表现 | 风险 | 优先级 |
|---|---|---|---|---|
| S1 | 每次路由全量重绘 | 单次 < 1 ms | 当前无感；数据量 10 倍后会掉帧 | P3 |
| S2 | 快照全量序列化 | 52.4 KB / 次 | 每次保存都写全量，操作频繁时可能有卡顿 | P3 |
| S3 | 无虚拟滚动 | 34 张表全量 DOM | 单个列表超 300 行会明显卡 | P3 |
| S4 | 定时器泄漏风险 | 日志计时器在 route 时清理 | 已处理，但新增定时器容易忘 | P2 |
| S5 | 无缓存层，重复全表扫描 | `flatMap` 遍历在多处重复 | 数据量大时叠加 | P3 |

**结论**：性能目前不是瓶颈，真正的风险集中在 E1 / E2 这类「一处出错就全站失效」的问题上。

## 七、建议的三个批次

**第一批（P0 四项）**：只做健壮性与交互惯性，不改功能。做完原型「点不坏」，评审时可以随便点。

**第二批（P1 前三项）**：配置治理闭环——影响面、发布单、镜像凭据。这三项构成私有云客户最关心的「配置与密钥怎么管」。

**第三批（P1 其余 + P2）**：列表能力、审计、平台运维、引导动线。

## 八、需要产品先定的两件事

1. **环境覆盖规则**：环境之间的配置是「继承 + 覆盖」还是「各存一份」？前者省事、后者清晰，会直接决定 F1 的数据结构。
2. **平台运维范围**：安装、升级、巡检要做到什么程度——只展示状态，还是要能触发升级？这决定 F6 是做一个页面还是一个流程。
