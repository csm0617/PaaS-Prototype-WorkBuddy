# 工作负载配置管理：能力梳理与实现建议

> 基于当前代码（HEAD `8892a95`）盘点，只列**尚未实现或只做了一半**的能力。

## 一、现状盘点

### 已实现

| 能力 | 实现位置 | 说明 |
|---|---|---|
| 应用级配置项 | `DB.config[appId]` | `{id, key, value, scope, mount, path, secret, note, updated}` |
| 生效范围 | `configOf(app, compName)` | `scope` 取 `all`（全部组件）或组件名 |
| 两种注入方式 | `effectiveEnv` / `ioVolumes` | `env` 注入环境变量；`file` 按目录合并成 ConfigMap / Secret 卷 |
| 工作负载自有变量 | `w.env` | 与同名应用配置**覆盖**，仅影响本负载 |
| 存储卷 | `w.volumes` | PVC / emptyDir，含存储类、访问模式、容量 |
| YAML 渲染 | `wlYamlView` | 密钥走 `secretKeyRef`、secret 卷，不写明文 |
| 隐蔽与显示 | `cfgReveal` / `ioReveal` | 密钥值默认打码 |
| 级联清理 | `cfgDelete` / 删组件 | 删组件清其作用域配置，删应用清全部 |

### 核心结论

现有模型是 **「应用级配置 + 工作负载级覆盖」** 的两层结构，抽象方向是对的（密钥集中维护、避免逐负载轮换）。缺的不是「能不能配」，而是**配了之后的可控性**：不知道谁在用、改了要不要重启、能不能回滚、值有没有泄漏。

## 二、功能清单

优先级定义：**P0** 不补就是坑；**P1** 影响日常使用效率；**P2** 安全与治理；**P3** 锦上添花。

### A. 引用关系与影响面

**A1 配置反向引用索引** · P0
- 用途：从 ConfigMap/Secret 的每个 key 反查「哪些工作负载在用、用的哪个 scope」。
- 场景：改 `ORDER_TIMEOUT_MS` 前先看清会波及哪 5 个负载，而不是改完等告警。
- 关系：与 `effectiveEnv` / `ioVolumes` 同源；是 A2、A3 的前置。
- 依赖：无需改数据结构，扫描现有 `configOf` + `w.env` 建映射即可。

**A2 变更影响面确认弹窗** · P0
- 用途：保存配置前弹出「影响 N 个组件 / M 个工作负载，其中 K 个需重启」。
- 场景：生产环境改共享配置，必须二次确认。
- 关系：与模块开关无关，属内核能力；与环境的「严格模式」联动（严格模式下强制审批）。
- 依赖：A1。

**A3 删除 / 改名保护** · P0
- 用途：被引用的 key 不允许直接删除，只能「先解绑」或「级联删除并列出清单」。
- 场景：误删 `DB_PASSWORD` 导致三个服务同时 CrashLoop。
- 关系：与级联清理逻辑（`cfgDelete`）冲突，需先改判定。
- 依赖：A1。

**A4 配置来源链路视图** · P0
- 用途：工作负载详情里展示 `负载 → 配置项 / 密钥 → key` 的完整来源链，可下钻。
- 场景：排查「这个环境变量到底从哪来的」，尤其是被同名覆盖时。
- 关系：与组件拓扑同构，可复用同一种渲染思路；是 YAML 页签的可视化版本。
- 依赖：A1。

### B. 注入方式与语义

**B1 热更新语义标注** · P0
- 用途：明确标出「环境变量方式改完必须重建 Pod；文件卷方式可热更新（受 kubelet 同步周期约束）」。
- 场景：改完配置发现没生效，实际是没重启。
- 关系：与「重启」按钮、发布流水线联动，可直接提供「改完并滚动重启」一键操作。
- 依赖：`mount` 字段（已有）。

**B2 checksum 注解自动滚动** · P1
- 用途：配置变更时给 Pod 模板打 `checksum/config` 注解，自动触发滚动更新。
- 场景：避免「配了但没生效」这类最高频的运维问题。
- 关系：与 CI/CD 的发布单绑定，配置变更也算一次发布。
- 依赖：B1、A1。

**B3 envFrom 全量注入** · P1
- 用途：把整个 ConfigMap/Secret 的所有 key 一次性注入，不用逐条声明。
- 场景：第三方中间件配置项多达几十个，逐条维护不现实。
- 关系：与现有「按 key 精确注入」并存，需在 `effectiveEnv` 增加来源类型枚举。
- 依赖：`effectiveEnv` 结构改造（从 `{key,value}` 扩展为 `{key, valueFrom}`）。

**B4 fieldRef / resourceFieldRef** · P1
- 用途：把 Pod 自身的 `POD_NAME`、`NODE_NAME`、`NAMESPACE`、以及 CPU/内存 limit 注入为环境变量。
- 场景：日志打点需要实例名；JVM 堆大小按 limit 百分比推导（现在 `JAVA_TOOL_OPTIONS` 是写死的）。
- 关系：与「指标」页签的资源配置直接对应，可做到「配了 limit 自动算出堆大小」。
- 依赖：无。

**B5 文件挂载的细粒度控制** · P1
- 用途：支持 `subPath`（只挂单个文件不覆盖目录）、`items`（选择性挂载部分 key）、`defaultMode`（文件权限）。
- 场景：挂 `application.yaml` 到 `/etc/app/` 而不冲掉目录里其他文件；证书文件需要 `0400`。
- 关系：当前「按目录合并成卷」的做法在单文件场景会误覆盖，属于现有实现的天花板。
- 依赖：`ioVolumes` 的合并逻辑要改成「目录级 + 文件级」两套路径。

**B6 外部密钥引用** · P2
- 用途：`valueFrom` 指向 Vault / 云 KMS / Secret Manager，平台只存引用不存值。
- 场景：金融、医疗等有密钥托管合规要求的客户。
- 关系：与 Secret 类型化（C1）配套；与审计（D2）强相关。
- 依赖：C1、D2、外部系统接入。

### C. 密钥专项

**C1 Secret 类型化** · P1
- 用途：从 `secret: true/false` 升级为带类型：`Opaque` / `kubernetes.io/tls` / `dockerconfigjson` / `basic-auth` / `ssh-auth`。
- 场景：TLS 证书需要 cert+key 两个键成对校验；拉私有镜像需要 imagePullSecrets，现在完全没有入口。
- 关系：与「访问入口」页签的 TLS 状态联动——证书来源就是这里的 Secret；与镜像仓库配置联动。
- 依赖：数据结构扩展（`type` + 多键结构），波及表单、YAML 渲染、`ioVolumes` 合并规则。

**C2 存储加密与轮转** · P1
- 用途：落库前信封加密（KMS 主密钥 + 数据密钥），支持「一键轮转」并记录轮转历史。
- 场景：密钥明文存数据库是最常见的合规硬伤；轮转后要能确认哪些负载已加载新值。
- 关系：与 C1、D1 强耦合；轮转需要触发 B2 的滚动重启。
- 依赖：平台侧密钥管理服务；原型阶段可先用「加密状态」字段占位。

**C3 明文读取审计** · P1
- 用途：谁在什么时候点了「显示」、看了哪个密钥，全部留痕，并支持按密钥反查。
- 场景：内部威胁排查；等保/审计要求。
- 关系：与 RBAC 联动——开发者应能「引用但不能查看」。
- 依赖：`cfgReveal` / `ioReveal` 埋点（已有入口，改造成本低）。

**C4 值强度与格式校验** · P2
- 用途：密码长度/字符集、TLS 证书有效期与域名匹配、JSON/Base64 格式校验。
- 场景：证书过期是线上事故的高频原因，且很难在发布前发现。
- 关系：与「访问入口」的证书到期提醒是同一个数据源。
- 依赖：C1。

### D. 版本、环境与治理

**D1 配置版本历史与回滚** · P1
- 用途：每次修改留快照，支持 diff 对比与一键回滚到任意版本。
- 场景：改错配置需要 30 秒内恢复，而不是凭记忆改回去。
- 关系：与 CI/CD 的发布记录打通——一次发布应同时锁定「镜像版本 + 配置版本」。
- 依赖：配置实体加 `revision`；回滚要能触发 B2。

**D2 环境维度覆盖** · P1（改动最大）
- 用途：同一 key 在 prod / staging / dev 取不同值，而不是复制三份配置。
- 场景：数据库地址、外部网关 URL 天然按环境不同——现在 `DB.config` 只按 `appId` 存，**根本表达不了**。
- 关系：与环境的「严格模式」联动；与「应用详情」的环境集合对应。这是当前模型最大的结构性缺口。
- 依赖：`DB.config` 的 key 从 `appId` 改为 `appId + env`，波及 `configOf`、`effectiveEnv`、`ioVolumes`、`cfgUsers`、YAML 渲染和全部表单。

**D3 配置漂移检测** · P2
- 用途：对比「平台声明值」与「集群实际值」，不一致时告警。
- 场景：有人 `kubectl edit` 直接改了 ConfigMap，平台不知情。
- 关系：与告警中心、工作负载「事件」页签联动。
- 依赖：需要「实际值」这一数据源（原型可模拟）。

**D4 GitOps / SealedSecret 来源标注** · P2
- 用途：标记配置是「平台维护」还是「Git 同步」，后者在平台内只读。
- 场景：已上 GitOps 的团队，平台不能成为第二个真相源。
- 关系：与 CI/CD 流水线的配置来源一致。
- 依赖：D1、D3。

**D5 配额与体积约束** · P2
- 用途：单 ConfigMap 1MiB 上限、应用内配置项数量上限、单密钥长度上限。
- 场景：把整个证书链塞进环境变量导致 Pod 起不来。
- 关系：与环境配额、应用配额一起展示。
- 依赖：无。

### E. 编辑效率

**E1 批量导入 / 导出** · P2
- 用途：导入 `.env`、`application.yaml`、`kubectl create secret` 生成的 YAML；导出为可提交的清单。
- 场景：从旧系统迁移、从本地开发环境同步配置。
- 关系：与 YAML 页签共用解析与渲染逻辑。
- 依赖：C1（类型识别）。

**E2 配置模板与跨应用复制** · P3
- 用途：把一组常用配置存为模板（如「标准 MySQL 连接串」），新应用一键套用。
- 场景：同一个中间件被 20 个应用接入。
- 关系：与应用创建向导联动。
- 依赖：D2（模板要按环境展开）。

**E3 配置引用可视化** · P3
- 用途：在组件拓扑上叠加「配置依赖边」，看清哪些组件共享同一个密钥。
- 场景：评估密钥轮换的爆炸半径。
- 关系：复用组件拓扑的布局算法（`layoutGraph`）。
- 依赖：A1。

## 三、优先级与依赖链

```
A1 反向引用索引
 ├─ A2 影响面确认
 ├─ A3 删除保护
 ├─ A4 来源链路视图
 └─ E3 拓扑叠加（P3）

B1 热更新语义 ── B2 checksum 滚动 ── C2 轮转后生效确认
B3 envFrom ── B4 fieldRef        （同属 effectiveEnv 结构改造）
B5 文件挂载细粒度                （独立，改 ioVolumes）
C1 Secret 类型化 ── C3 审计 / C4 校验 / B6 外部密钥 / E1 导入
D2 环境维度覆盖                  （改动最大，建议单独立项）
D1 版本历史 ── D3 漂移 ── D4 GitOps
```

### 建议的实施批次

| 批次 | 内容 | 理由 |
|---|---|---|
| 第 1 批 | A1 → A2 → A3 → A4 → B1 | 全在现有结构内，不改数据模型，一周内可闭环，直接消除「改配置心惊胆战」的体验问题 |
| 第 2 批 | D2 环境维度 | 唯一的**结构性**缺口，越晚改代价越大（波及 6 处函数 + 全部表单） |
| 第 3 批 | C1 → B3/B4 → B5 | 能力扩展，改 `effectiveEnv` / `ioVolumes` 两处核心函数，需一次性做完避免反复 |
| 第 4 批 | D1 → B2 → C2/C3 | 治理能力，依赖前面稳定后的实体结构 |
| 第 5 批 | D3/D4/E1/E2/E3 | 锦上添花，可按客户需求点单 |

**关键判断**：第 1 批之所以排最前，不是因为简单，而是因为它把「配置」从**一堆键值对**变成**有引用关系的对象**。没有这层，后面所有治理能力（回滚、轮转、漂移）都无处附着。

## 四、与三大模块的交叉点

| 模块 | 交叉点 | 说明 |
|---|---|---|
| **Service Mesh** | mTLS 证书即 Secret | 证书轮换走 C2，与 Sidecar 注入状态联动；Mesh 关闭时证书管理入口应一并收缩 |
| **云边端协同** | 配置下发状态 | 边缘节点配置版本落后需单独展示（离线节点用本地缓存副本）；与「应用分发」页签同源 |
| **CI/CD** | 配置随发布单快照 | 一次发布锁定「镜像 + 配置」两个版本；配置变更应可作为独立发布触发 B2；构建号注入（`BUILD_ID` / `GIT_SHA`）走 B4 |
| **存储** | 挂载点冲突 | ConfigMap/Secret 卷与 PVC 卷共用 `volumeMounts` 命名空间，需检测路径重复 |
| **告警** | 配置错误 → CrashLoop | 「事件」页签里应能关联到具体哪个 key 导致的启动失败 |
| **RBAC** | Secret 读取权限 | 「可引用不可查看」需要在 A4 的来源链上就做裁剪，而不是只在 UI 打码 |
| **环境** | 严格模式 | 生产环境应禁止热改配置，强制走发布单 |

## 五、数据模型改动草案

```js
// 现状
DB.config[appId] = [{ id, key, value, scope, mount, path, secret, note, updated }]

// 建议
DB.config[appId] = [{
  id, key, type,            // type: Opaque | tls | dockerconfigjson | basic-auth
  value,                    // 多键类型改为 { cert, key } 等对象
  scope, mount, path,
  secret, encrypted,        // 加密状态，替代裸明文
  env,                      // 可选：仅在某环境生效，null 表示全环境
  revision, history: [],    // 版本快照
  source                    // 'platform' | 'gitops'
}]

// 工作负载侧
w.env = [{ key, value, valueFrom }]   // valueFrom: {type:'secretKeyRef'|'fieldRef'|'envFrom', ...}
w.volumes = [{ ..., subPath, items, defaultMode, readOnly }]
```

改动集中在两个函数：`effectiveEnv()`（来源解析）和 `ioVolumes()`（卷构造）。这两个函数是所有页面和 YAML 渲染的唯一出口，**改造收口在这两处，UI 层不受连带影响**——这是当前代码结构做得好的一点。

## 六、如果只做三件事

1. **A1 + A2**：配置的反向引用与变更影响面。成本最低，体验提升最直接。
2. **D2**：环境维度。不补，这个平台在生产环境就是用不了。
3. **B1 + B2**：热更新语义 + 自动滚动。消除最高频的「为什么没生效」问题。
