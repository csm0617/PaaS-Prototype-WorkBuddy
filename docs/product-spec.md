# 产品功能地图与业务规则 v0.1

> 定位：私有云 · 整套交付 · 单租户。用途：内部评审对齐，后端按此实现。
> 状态标记：✅ 已闭环（可增删改且落盘） / ◐ 半成品（有界面无逻辑） / ○ 未做 / ✕ 已砍

---

## 一、产品边界

**做什么**：给企业一套开箱可用的云原生应用平台，业务团队不用懂 K8s 就能交付应用；平台自带底座，客户不感知底层集群。

**不做什么**（已确认砍掉）：企业空间与多租户隔离、项目配额与审批、成本分摊与计费、应用商店与模板市场、跨集群纳管与多区域调度。

**四条故事线**（评审要都能讲通）

| 故事线 | 一句话 | 支撑页面 |
|---|---|---|
| 三层模型 | 应用 → 组件 → 工作负载，分别对应业务、构建、调度三种边界 | 应用详情、组件拓扑、工作负载 |
| 模块解耦 | Mesh / 云边端可关，关了 UI 收缩但基础功能不塌 | 模块管理、应用详情、工作负载 |
| 配置治理 | 配置集中维护、密钥不落明文、改前知影响 | 配置与密钥、配置与存储 |
| 发布链路 | 组件 → 流水线 → 制品 → 灰度 → 回滚 | 流水线、发布记录、访问入口 |

## 三、核心业务流程

### 流程 1：应用上线

```
新建应用（向导）→ 添加组件（绑定镜像与版本）→ 创建工作负载（副本/资源/调度位置）
   → 绑定流水线 → 运行流水线（构建→扫描→推镜像→部署预发→审批→生产）
   → 生成发布单 → 审批 → 灰度（按 Mesh 权重）→ 全量 → 记录版本
```

关键节点：审批在生产阶段前；灰度依赖 Mesh，Mesh 关闭时退回原生滚动更新。

### 流程 2：配置变更

```
新增/修改配置（作用域：全部组件 或 指定组件）
   → 选择注入方式（环境变量 / 文件挂载）
   → 【待定】是否走发布单
   → 生效：环境变量需重建 Pod；文件挂载可热更新
```

### 流程 3：故障处置

```
告警产生 → 认领（责任到人）→ 定位（跳转工作负载：日志/事件/指标/链路）
   → 处置（重启/扩容/回滚/改配置）→ 关闭（需填原因）
```

## 四、业务规则

### 4.1 状态机

**应用**

```
运行中 ⇄ 已停止
   ↘ 异常 ↗
```

- 「已停止」= 全部工作负载副本为 0
- 「异常」= 存在就绪率低于阈值的运行中工作负载
- 状态由工作负载聚合推导，**不手工设置**（当前实现是硬编码数字，见第六节）

**组件**

无独立运行时状态，健康度 = 其下工作负载就绪率加权。

**工作负载**

```
待调度 → 运行中 ⇄ 已停止
   ↘ 异常（CrashLoop / 就绪探针失败）
定时任务：待执行 → 运行中 → 已完成 / 失败
```

**发布单**

```
待审批 → 待执行 → 发布中 → 成功
                      ↘ 失败 → 已回滚
```

**告警**

```
未处理 → 处理中 → 已关闭
   ├→ 已忽略（需填原因，永久）
   └→ 静默（需填时长，到时自动恢复未处理）
```

### 4.2 约束规则

编号便于评审逐条过。

| 编号 | 规则 | 当前实现 |
|---|---|---|
| R-01 | 工作负载的镜像版本只能继承组件版本，不可单独改 | ✅ 已遵循（展示为只读） |
| R-02 | 组件版本只能通过发布推进，不能手改 | ❌ 组件配置弹窗可直接改 version |
| R-03 | 删除工作负载前须确认副本为 0 或已停止 | ✅ 有确认弹窗 |
| R-04 | 删除组件前须无运行中工作负载 | ❌ 只提示「这是最后一个组件」 |
| R-05 | 删除应用前须无运行中工作负载，或二次确认 | ◐ 仅需输入名称，P0 应用也能直接删 |
| R-06 | 被引用的配置项不可直接删除，须先解绑 | ❌ 无拦截 |
| R-07 | 同一作用域内配置 key 唯一 | ✅ 已校验 |
| R-08 | 密钥值默认不可见，查看需权限并留痕 | ◐ 可点「显示」，无权限判断、无审计 |
| R-09 | 生产环境变更须审批 | ◐ 流水线有审批节点，配置变更无 |
| R-10 | 回滚只能回到最近一个成功版本 | ✅ 已限定 |
| R-11 | 组件改名不影响依赖、配置作用域、访问入口 | ✅ 已实现（按 id 引用） |
| R-12 | 同一应用内组件名唯一、同一组件内负载名唯一 | ✅ 已校验 |
| R-13 | 边缘节点离线时，其上负载保持最后配置运行 | ◐ 分发策略里有「断网自治」描述，无实际状态 |
| R-14 | 模块关闭后，相关数据保留，重新开启即恢复 | ✅ 已实现 |

| 场景 | 应有表现 | 当前 |

## 六、现有实现与规则的冲突

这四处不是"没做"，而是**做错了**，评审时会被问住：

1. **R-02 违反**：组件配置弹窗能直接改「镜像版本」，等于绕过发布流程。版本应该只读，由发布写入。
2. **应用健康度是硬编码**：`app.health` 在数据里写死成 99.2 这类数字，没有从工作负载就绪率推导。停掉所有负载，健康度还是 99.2。
3. **R-05 偏松**：删除 P0 应用只要求输名字，没有「存在运行中负载则阻止」的判断。
4. **告警认领是假的**：点了弹个提示，状态不变、没有责任人、没有时间戳。

## 七、待你拍板

三处业务流程有分叉，我给了建议值，你改或确认：

**Q1｜生产发布是否强制审批？**
建议：是。P0 应用需两人（应用负责人 + 运维值班），P1/P2 单人即可。
理由：私有云客户多为内部系统，P0 停机的代价远高于审批的摩擦。

**Q2｜配置变更走不走发布单？**
建议：走。配置变更生成独立发布单，带快照、可回滚。
理由：配置错误是线上事故的高频原因，且现在回滚能力只覆盖镜像版本，配置改错了没法退。

**Q3｜告警分级与响应要求？**
建议：严重（P0）5 分钟内响应、15 分钟未响应升级到负责人；警告（P1）30 分钟；提示（P2）次日处理。
理由：没有响应时限的分级没有意义，只是标签。
