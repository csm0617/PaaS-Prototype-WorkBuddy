# 应用 / 组件 / 工作负载：数据模型改进建议

> 基于 HEAD `8892a95` 的实际代码盘点。只列**当前结构支撑不了、或已经埋了坑**的地方。

## 一、现状模型解剖

```
DB.apps[]                         ← 树形嵌套，不是规范化实体表
 └─ { id, name, domain, owner, level, status, health,
      desc, updated, envs:['生产环境'], components:[], pipelines:[], events:[] }
     └─ components[]              ← 无 id，name 即主键
        └─ { name, role, runtime, image, version, workloads:[] }
           └─ workloads[]         ← 无 id，name 即主键
              └─ { name, kind, ready:'4/4', image,
                   cpu:'1.8 / 8c', mem:'4.2 / 8Gi',
                   status, where, cluster, mesh, restarts, age, env[], volumes[] }

DB.deps[appId]   = [[from, to, label, kind]]   ← 四元组数组
DB.config[appId] = [{ id, key, value, scope }] ← scope 存组件名
DB.access[appId] = [...]                       ← 按 appId 平铺
DB.envs[]        = [{ name, code, ... }]       ← 全局环境表
```

一句话概括：**树形嵌套 + 四个平行的 `appId → xxx` 映射 + 名字做外键**。

这个结构在演示阶段完全够用，但一旦要做「重命名组件」「批量操作」「变更审计」「按环境覆盖」，四处都会漏水。

---

## 二、已识别的结构性问题

### P1　组件与工作负载没有 ID，name 兼任主键

**证据**：`DB.deps[appId]` 的边是 `[组件名, 组件名, ...]`；`config.scope` 存组件名；路由 `#/apps/{id}/{comp}/{wl}` 用名字；`cfgUsers()` 靠 `scope === compName` 匹配。

**后果**：重命名一个组件 = 依赖边断裂、配置作用域失效、书签与深链接 404、历史记录对不上。真实平台里改个组件名是常规操作，这里做不了。

**这是最该修的一项**，因为它污染了所有引用点，越晚改涉及面越大。

### P2　拓扑依赖没有被持久化

**证据**：`saveSnapshot()` 的白名单里没有 `deps`（第 79 行附近的字段清单），但第 1327 行确实在改 `DB.deps`——依赖连线是可编辑的。

**后果**：刷新页面后，用户手动添加的依赖边全部丢失。这是**当前的 bug**，不是设计问题。

### P3　持久化靠手写字段白名单

**证据**：`saveSnapshot` 逐字段列举 14 个键；`loadSnapshot` 再逐字段判断 `Array.isArray` 后赋值。

**后果**：新增一个实体（如 `deps`）必须记得在两处同步改，漏一处就静默丢数据。事实上已经漏了一次。

### P4　数值字段是格式化字符串

**证据**：`ready: '4/4'`、`cpu: '1.8 / 8c'`、`mem: '4.2 / 8Gi'`，展示时靠 `parseRes()` 反解析，再靠 `fmtQty()` 格式化回去。

**后果**：无法排序、无法聚合、无法算容量水位、无法做 HPA 建议。字符串一旦拼错（如 `'4/4 '`）解析就静默失败。

### P5　镜像版本双写

**证据**：组件上 `version: 'v2.4.1'`，每个工作负载又各存一份 `image: 'v2.4.1'`。而 `order-db` 的 image 是 `'mysql:8.0.34'`——它根本不来自组件构建产物。

**后果**：两处不同步时无法判断哪个是真的；也无法区分「组件构建的镜像」和「引用的第三方镜像」，而这两者的升级语义完全不同。

### P6　环境是字符串

**证据**：`app.envs: ['生产环境']`，而 `DB.envs[].code` 是 `'prod'`。匹配靠中文名。

**后果**：环境改名即断链；且配置没有环境维度（见另一份文档），两者是同一个病根。

### P7　关系只能表达「一条线」

**证据**：`DB.deps` 是 `[from, to, label, kind]` 四元组，`kind` 只用来判断是否 async。

**后果**：想加协议、权重、超时、是否跨集群，只能往数组尾部塞第五、第六个元素——调用方全部要改，且语义靠位置记。

### P8　删除是手写清理，不是级联钩子

**证据**：删组件时手写 `DB.deps` 过滤（7187）、配置过滤（7186）；删应用时逐项 `delete DB.deps[app.id]`（7215）。

**后果**：每新增一个模块（告警、访问入口、流水线绑定）都要记得回来加一行。漏了就是悬挂引用——而悬挂引用在树形结构里不会报错，只会静默显示为空。

## 三、改进建议

### A 组：数据模型

**A1 引入稳定 ID，name 降级为展示属性** · **P0**
- 做法：组件与工作负载各加 `id`（短码，如 `cmp_a1b2` / `wl_c3d4`），所有跨实体引用改存 id，name 仅用于展示与唯一性校验。
- 适用场景：任何允许重命名的平台。改组件名、迁移工作负载、复制应用到另一环境，都依赖稳定标识。
- 依赖：需要一次性迁移（见第五节），并改路由参数。
- 影响面：`deps`、`config.scope`、`access`、路由、所有 `find(c => c.name === ...)`。

**A2 结构化数值字段** · **P1**
- 做法：`ready: {ready: 2, desired: 2}`、`resources: {cpu: {req: 0.5, limit: 2}, mem: {req: 1, limit: 4}}`（单位统一为核 / GiB 的数字），展示层负责格式化。
- 适用场景：容量水位、配额核算、排序筛选、扩缩容建议。现在「按 CPU 排序」根本做不了。
- 依赖：`parseRes` / `fmtQty` 改为纯展示工具。
- 影响面：列表页、详情页、概览统计、YAML 渲染。

**A3 镜像版本单一真相源** · **P1**
- 做法：组件存 `{image, version, digest}`；工作负载只存 `imageRef`（指向组件，或 `{type:'external', ref:'mysql:8.0.34'}`）。
- 适用场景：强制「工作负载版本必须继承组件版本」这条约束；同时保留第三方镜像的正常表达。
- 依赖：A1（引用要稳定）。
- 影响面：发布、回滚、YAML、镜像更新工作流。

**A4 labels / annotations 通用扩展位** · **P0（成本最低）**
- 做法：三层实体都加 `labels: {}` 与 `annotations: {}`。
- 适用场景：批量操作（「所有 `tier=backend` 的负载重启」）、策略绑定、成本归集、灰度标记（`track=canary`）。
- 为什么优先级高：它是**避免模型膨胀的唯一手段**。现在 `where`、`role`、`kind`、`mesh` 全是特设字段，每来一个需求就加一个字段；有了 labels，多数需求不用改 schema。
- 依赖：无。

**A5 状态机化** · **P2**
- 做法：`status` 从自由中文串改为枚举 + 合法转移表（`Pending → Running → Degraded → Stopped`）。
- 适用场景：状态驱动的操作按钮（停机的负载不该显示「重启」）、健康度自动推导。
- 依赖：A2（健康度需要结构化指标才能算）。

### B 组：关联关系表达

**B1 用关系表替代四元组** · **P1**
- 做法：
  ```js
  DB.edges = [{ id, from, to, type, protocol, weight, timeout, async }]
  // type: 'calls' | 'publishes' | 'reads' | 'mounts' | 'schedules' | 'exposes'
  ```
- 适用场景：拓扑图要区分「同步调用 / 异步消息 / 数据读写」；流量治理要按边配置超时与权重。
- 依赖：A1（from/to 存 id）。
- 收益：加属性不再改调用方，且不同 `type` 可以有不同的渲染与校验规则。

**B2 关系基数与方向语义显式化** · **P1**
- 做法：明确 `from` 是调用方（现在代码注释里是「[上游, 下游]」，但 UI 上容易被理解反）；建边时校验：不许自环、不许跨应用（除非显式声明外部依赖）、不许成环（或至少告警）。
- 适用场景：组件拓扑自动布局依赖方向正确，否则分层会算反。
- 依赖：B1。

**B3 外部依赖实体化** · **P2**
- 做法：组件加 `kind: 'internal' | 'external'`，外部组件可以没有工作负载，只有连接信息。
- 适用场景：支付网关依赖银行接口、应用依赖外部 Redis——现在拓扑里只能画个假节点，且不计入健康度。
- 依赖：B1。

**B4 引用表 + 引用计数** · **P1**
- 做法：统一 `refs: { target: 'cfg-xxx', from: 'wl_yyy', field: 'env' }`，删除前反查。
- 适用场景：配置、密钥、存储类、访问入口都要用；是「删除保护」和「影响面分析」的共同地基。
- 依赖：A1。
- 说明：这份能力在配置管理文档里作为 A1 提过，这里是它在模型层的落点。

**B5 组件契约建模** · **P2**
- 做法：组件加 `contract: { ports: [], protocol, apiVersion, healthPath }`。
- 适用场景：访问入口自动生成路由（现在要手填后端端口）、拓扑边自动标注协议、Mesh 流量规则按端口匹配。
- 依赖：B1。

### C 组：扩展性

**C1 schema 版本 + 迁移链** · **P0**
- 做法：`DB.schemaVersion = 2`，配套 `migrations = { 1: v1→v2, 2: v2→v3 }`，启动时顺序执行。
- 适用场景：任何结构变更。现在 `normalizeIO()` 就是雏形，但它只补字段、不带版本，也无法回退。
- 依赖：无。
- 收益：把「改结构」从高风险操作降为常规操作。

**C2 持久化改为注册表驱动** · **P0**
- 做法：集中声明 `PERSIST = [{key:'apps'}, {key:'deps'}, {key:'config'}, ...]`，save/load 遍历它，不再手写白名单。
- 适用场景：直接修掉 P2 和 P3。
- 成本：约 20 行代码，零风险。

**C3 工作负载 kind 插件化** · **P2**
- 做法：`KINDS = { Deployment: {fields, yamlTpl, canSchedule:['云端'], mesh:true}, EdgeApp: {...} }`。
- 适用场景：新增一种负载类型（如 Job、DaemonSet、Serverless 函数）时不用改五处分支。现在 `normalizeIO`、`whereChip`、YAML 渲染、表单里都有 kind 分支。
- 依赖：A2（字段结构化后模板才好写）。

**C4 策略/守卫层** · **P2**
- 做法：独立的 `guards = [{match, check, message}]`，在变更前统一执行，与实体定义解耦。
- 适用场景：「P0 应用不允许删最后一个工作负载」「镜像必须继承组件版本」「边缘负载必须指定节点亲和」。
- 依赖：B4（判断需要引用信息）。
- 收益：规则可配置、可开关，而不是散落在各个 handler 里的 if。

**C5 变更审计实体化** · **P1**
- 做法：`DB.audit = [{ts, who, entity, entityId, action, before, after}]`，所有写操作统一埋点。
- 适用场景：变更追溯、回滚依据、合规审计、活动流（现在「事件」是各应用手写的假数据）。
- 依赖：A1 + C2。

### D 组：可维护性

**D1 派生索引缓存** · **P1**
- 做法：构建一次 `{ byWlId, byCompId, wlList }`，写操作后失效重建。
- 适用场景：全局工作负载页、搜索、`cfgUsers` 现在都在做多层 `flatMap` 全表扫描。
- 依赖：A1。

**D2 级联删除钩子** · **P1**
- 做法：`onDelete('component', fn)` 注册清理器，删除统一走 `cascade()`。
- 适用场景：修掉 P8。新增模块时注册一次即可。
- 依赖：B4。

**D3 命名唯一性约束** · **P1**
- 做法：同应用内组件名唯一、同组件内负载名唯一，创建/改名时校验。
- 适用场景：A1 落地后 name 不再是主键，但仍需唯一（否则展示层无法区分）。
- 依赖：A1。

**D4 演示数据生成器** · **P3**
- 做法：用模板函数生成 N 个应用，替代 300 行手写 JSON。
- 适用场景：压力测试、多租户演示、不同规模下的布局验证。
- 依赖：无。

## 四、业务功能新增点

模型之外，三层结构上还缺这些能力：

| 功能 | 说明 | 优先级 | 依赖 |
|---|---|---|---|
| 应用模板 / 脚手架 | 新建应用时选模板（如「Java 微服务」）自动生成组件骨架、流水线、默认配置 | P1 | B5、C3 |
| 组件多版本并存 | 同一组件同时存在 stable / canary 两个版本，而不是建两个组件 | P2 | A3 |
| 健康度自动推导 | 现在 `health` 是写死的数字，应由组件健康加权得出 | P1 | A2、A5 |
| 变更单 / 发布窗口 | 应用级变更需审批，带时间窗约束 | P2 | C5 |
| 负责人实体化 | `owner` 现在是字符串「张明」，应对接用户实体，支持转交与离职回收 | P2 | — |
| 成本分摊 | 按工作负载资源 × 单价归集到应用 / 业务域 | P3 | A2、A4 |
| 应用级依赖视图 | 跨应用调用关系（现在拓扑只到应用内部） | P3 | B1、B3 |

## 五、改造路线

不要重写。按「先修漏水，再改结构」的顺序推进：

| 批次 | 内容 | 风险 | 说明 |
|---|---|---|---|
| **第 0 批** | C2 注册表持久化 + 修复 deps 丢失 + A4 labels 字段 | 极低 | 约 30 行，先止血 |
| **第 1 批** | C1 迁移链 + A1 稳定 ID + D3 唯一性校验 | 中 | 一次性迁移，之后所有改动都轻松 |
| **第 2 批** | B1 关系表 + B4 引用表 + D2 级联钩子 | 中 | 三者互相依赖，一起做 |
| **第 3 批** | A2 结构化数值 + A3 镜像真相源 + D1 索引 | 中 | 影响所有列表与统计页 |
| **第 4 批** | A5 状态机 + C3 插件化 + C4 守卫 + C5 审计 | 较高 | 在稳定结构上叠加治理能力 |

### 迁移策略（v1 → v2）

```js
// 生成 id、把名字引用换成 id 引用
function migrate1to2(db) {
  const idOf = {};
  db.apps.forEach(a => a.components.forEach(c => {
    c.id = c.id || shortId('cmp');
    c.workloads.forEach(w => {
      w.id = w.id || shortId('wl');
      idOf[`${a.id}/${c.name}/${w.name}`] = w.id;
    });
  }));
  Object.keys(db.deps || {}).forEach(appId => {
    db.deps[appId] = db.deps[appId].map(([f, t, label, kind]) => ({
      id: shortId('e'), from: f, to: t, type: 'calls',
      label, async: kind === 'async'
    }));
  });
  Object.keys(db.config || {}).forEach(appId => {
    db.config[appId].forEach(c => { c.id = c.id || shortId('cfg'); });
  });
  return { ...db, schemaVersion: 2 };
}
```

关键点：**迁移函数要把「名字引用」翻译成「id 引用」，而不是简单补字段**。否则 id 加了但引用还在用名字，等于白改。

## 六、如果只做四件事

1. **C2 + 修复 deps 持久化** —— 当前就在丢数据，成本最低
2. **A1 稳定 ID** —— 后面所有关联能力的前提
3. **B1 关系表 + B4 引用表** —— 把「模型」从树升级为图
4. **A4 labels** —— 用扩展位替代加字段，让模型不再随需求膨胀
