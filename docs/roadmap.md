# 下一步做什么：优先级建议

> 基于 HEAD `0787fc8` 的代码盘点。结论先行：广度和模型底子都够了，**缺的是纵深与可交付形态**。

## 一、现状判断

**已经不错的部分**

| 维度 | 数据 |
|---|---|
| 页面覆盖 | 21 个导航路由，从概览到 RBAC 齐全 |
| 交互深度 | 59 处操作会真正改数据并落盘（不是纯展示） |
| 模型基础 | 三层实体有稳定 id、依赖按 id 引用、快照注册表驱动 |
| 可插拔 | Mesh / 云边端关闭后 UI 整体收缩，非简单隐藏 |

**明显的断层**

1. **6 个死按钮**——`告警规则`、`通知渠道`、`证书管理`、`扫描策略`、`批量固件升级`、`拉取指令`。样式上是可点按钮，实际没有绑定任何事件。评审时点一下没反应，比没有这个按钮更伤可信度。
2. **告警认领是假操作**——`onclick="toast('已认领')"`，不改状态、不写记录、不刷新列表。点了还是「未处理」。
3. **配置改动没有影响面**——改一个被 6 个工作负载引用的 key，保存前没有任何提示；删除被引用的 key 也不会被阻止。
4. **只能本机打开**——没有在线链接，分享需要对方拿到整个目录。

## 二、三个候选方向

| | A 治理纵深 | B 模型重构 | C 演示交付 |
|---|---|---|---|
| **做什么** | 配置影响面、删除保护、告警处置、审计 | 关系表对象化、引用表、级联钩子、结构化数值 | 在线发布、死按钮清零、引导动线、空态 |
| **谁受益** | 看配置治理的人（运维/架构） | 后续所有开发 | 每一个打开原型的人 |
| **可见度** | 高（可直接演示） | 零（纯内部） | 高（第一印象） |
| **投入** | 中 | 中大 | 小 |
| **风险** | 低，不动数据结构 | 中，会改所有读依赖的地方 | 极低 |
| **不做会怎样** | 演示时被问「改错了怎么办」答不上 | 第 3 批的改动会再来一遍 | 分享靠传文件夹 |

**取舍**：B 是欠债，但现在只有「依赖」和「配置作用域」两个使用方，抽象早了容易做错——等 A 做完会出现第三、第四个使用方，那时再抽引用表，接口才对得上。所以 **A 先做，B 在后**。C 里有一项成本极低、收益极高，应该插到最前面。

## 三、推荐顺序

### P0-1　死按钮清零 + 告警处置闭环

- **目标**：原型上不存在「点了没反应」的元素。
- **做法**：6 个死按钮按性质分两类——能落地的补交互（告警规则列表、通知渠道配置），暂不支持的改为明确置灰 + 悬浮说明「本期未开放」，而不是假装可点。告警认领改为真实状态流转（未处理 → 处理中 → 已关闭），写 `DB.alerts` 并落盘。
- **前置依赖**：无。
- **预期产出**：告警页可完整走一遍「看到 → 认领 → 关闭」；死按钮从 6 个降到 0。
- **规模**：S

### P0-2　配置影响面与删除保护

- **目标**：改配置前知道会波及谁，删配置时被拦住。
- **做法**：
  1. 建一次性反查（扫 `effectiveEnv` + `ioVolumes`），得出「这个 key 被哪些组件/工作负载引用」
  2. 保存前弹影响面：「影响 3 个组件 6 个工作负载，其中 4 个需重启」
  3. 删除被引用的 key 时拦截，列出引用方，只能「先解绑」
  4. 工作负载详情补一条来源链：`负载 → 配置项 → key`
- **前置依赖**：第 1 批的 id 与解析器（已完成）。
- **预期产出**：配置治理这条线能演示完整闭环，也是配置文档里 P0 的全部内容。
- **规模**：M

### P0-3　发布为在线链接

- **目标**：一条 URL 就能分享，不依赖对方拿目录。
- **做法**：静态站点直接托管，保留 hash 路由（当前路由机制天然兼容）。
- **前置依赖**：无。
- **预期产出**：可分享链接 + 一个固定入口页。
- **规模**：XS

### P1　关系表 + 引用表 + 级联钩子

- **目标**：把「树」升级为「图」，让删除与影响面分析有统一地基。
- **做法**：`DB.deps` 四元组改为对象（可承载协议、权重、超时）；建 `refs` 引用表；删除统一走 `cascade()` 钩子。
- **前置依赖**：P0-2 完成——此时反查逻辑已有两处使用方，抽象方向明确。
- **预期产出**：删除任一实体自动清理全部引用；影响面从"临时扫描"变为"查表"。
- **规模**：M

### P2　环境维度覆盖

- **目标**：同一个 key 在 prod / staging 取不同值。
- **做法**：`DB.config` 的键从 `appId` 改为 `appId + env`，波及 `configOf` / `effectiveEnv` / `ioVolumes` / `cfgUsers` / YAML 渲染 / 全部表单。
- **前置依赖**：P1 完成（配置实体结构稳定后再动维度）。
- **预期产出**：环境切换时配置值跟着变，这是当前模型最大的结构性缺口。
- **规模**：L

### P3　其余按需

结构化数值（可排序、可算水位）、审计日志、空态与错误态、成本分摊。这些不构成瓶颈，等有具体需求再排。

## 四、不建议现在做的

- **kind 插件化**：目前只有 5 种工作负载类型，没有第三种扩展需求，抽象是空转。
- **多租户 / 成本分摊**：没有对应场景，做了也是占位。
- **大改视觉**：当前设计系统已成型，改动收益低于成本。

## 五、需要你补充的上下文

这几项会直接改变上面的排序，麻烦确认：

1. **这个原型给谁看？** 内部评审、客户演示、还是需求文档配图？如果是客户演示，P0-3 要提到第一位，且要做引导动线。
2. **有没有要对照的参照平台？** KubeSphere / Rancher / 阿里云 ACK / 腾讯 TKE——如果评审方熟悉某个平台，交互偏离会被质疑。
3. **后端会真实实现吗？** 决定要不要补一层接口契约（请求/响应示例），还是永远保持纯静态。
4. **主故事线是哪一条？** 三层模型、模块解耦、配置治理、发布链路——四条都讲会散，需要挑一条做成完整闭环。
5. **有没有明确的评审时间点？** 有的话按时间倒排，砍掉非必需项。

# 修订：根据评审上下文调整（2026-10-30）

## 确认的上下文

| 问题 | 答复 | 对排序的影响 |
|---|---|---|
| 给谁看 | 内部评审 | 在线发布可后置（内部可本机/局域网），但仍值得做——成本极低 |
| 参照平台 | KubeSphere | 需要术语与概念对齐，否则评审第一句就是「这和 KubeSphere 什么关系」 |
| 后端 | 会真做，但先梳理产品与业务 | **技术债重构降级**：后端会用真数据库与真 schema，前端的模型抽象不再是最短路径 |
| 故事线 | 四条都要 | 需要一条主轴 + 三条纵向证据，而不是并列四个功能 |
| 时间点 | 无 | 按价值排序，不为日期裁剪；但不能无限铺开 |

## 关键调整

**1. 「梳理产品功能与业务」升为第 0 步**

理由是你自己给出的判断——产品规则没定清，后端做出来必然返工。具体要落成四份东西：

- **功能地图**：完整功能树，标注「已实现 / 有界面无逻辑 / 未做」
- **术语对照表**：我们 vs KubeSphere（见下表）
- **业务规则**：状态机（应用/发布/告警的生命周期与合法流转）、权限矩阵、配额规则
- **异常与边界**：空态、失败态、并发冲突、资源不足时的表现

**2. 模型重构（关系表 / 引用表 / 级联钩子）从 P1 降到 P3**

原计划假设前端模型要长期演进。但既然后端会用真数据库，schema 应该由后端定义、前端适配——现在花力气抽象前端数据结构，等于给一个会被替换的层做设计。**保留稳定 ID 与解析器即可**（已完成），其余等后端 schema 出来再说。

**3. 环境维度提前**

原排在 P2，理由是改动大。但既然会真做后端，多环境是必然要求，而且它属于「业务规则」而非「技术债」——应该在第 0 步就定清楚规则（哪些配置按环境覆盖、哪些全局共享），原型再跟上。

## KubeSphere 对齐：需要补的概念差

| 维度 | KubeSphere | 当前原型 | 处理建议 |
|---|---|---|---|
| 层级 | 企业空间 → 项目 → 应用/工作负载 | 业务域（弱）→ 应用 → 组件 → 工作负载 | 需要一张映射说明；多出的「组件」层要在评审时主动解释 |
| 配置 | 配置字典 / 密钥 | 配置项 / 密钥 | 术语统一为「配置字典」，避免评审时来回解释 |
| 工作负载类型 | 部署、有状态副本集、守护进程集、定时任务、守护进程 | Deployment / StatefulSet / CronJob / EdgeApp | 展示层用中文名，YAML 保留 kind |
| 应用 | 应用商店模板 + 项目内应用 | 只有业务应用 | 缺「应用模板」概念 |
| 全局视图 | 容器组列表、服务列表、监控中心、日志检索、审计日志 | 有工作负载列表，无全局 Pod/Service 视图 | 属于功能地图里要补的项 |
| 配额 | 项目配额、企业空间配额 | 仅有资源规格 | 属于业务规则里要定的项 |
| 告警 | 告警规则 + 通知渠道 + 通知历史 | 有告警列表，规则与渠道是死按钮 | 对应任务 1 |

**注意**：不必照搬 KubeSphere 的层级。「组件」这一层是我们的设计选择（构建单元 ≠ 调度单元），保留它，但要在功能地图里写清「为什么多一层」——否则评审会认为是没想清楚。

# 第二次修订：产品定位收紧（2026-10-30）

## 确认的定位

| 维度 | 结论 | 含义 |
|---|---|---|
| 部署形态 | **私有云，整套交付** | 客户不感知底层 K8s，平台自带底座 |
| 租户模型 | **单租户** | 一个客户一套平台，不需要企业空间与租户隔离 |
| 参照平台 | KubeSphere **仅作参考** | 不逐项对齐，保留自己的层级与命名 |

## 直接砍掉的能力

这些不再设计、也不占原型篇幅：

- **企业空间 / 多租户隔离**：单租户，不存在跨租户视角
- **项目配额 / 资源配额审批**：客户自己就是资源主人，配额由客户在底座层管理
- **成本分摊 / 计费**：私有云按合同交付，不按用量结算
- **应用商店 / 应用模板市场**：交付形态是定制项目，模板复用价值低
- **跨集群纳管 / 多区域调度**：一套平台对应一套底座

**保留**：RBAC（企业内部仍需角色分工，但只做「角色 × 动作」，不做租户维度）。

## 对现有原型的影响

| 现状 | 调整 |
|---|---|
| 运维中心 → 集群管理（含「接入集群」表单） | 降级为「平台底座」：节点、存储、网络只读视图，去掉纳管外部集群的入口 |
| 平台管理 → 角色权限 | 保留，文案从「租户管理员」类表述改为企业内部角色 |
| 三层模型（应用-组件-工作负载） | 不变，这是产品差异点 |
| 云边端协同、Service Mesh | 不变（未被裁掉） |

## 术语策略：不做对照表，只做「防误解」

原计划的逐项对齐取消。只对三个高频词做兼容，避免评审时反复解释：

| 建议用词 | 对应 K8s 概念 | 理由 |
|---|---|---|
| 配置字典 | ConfigMap | KubeSphere / K8s 用户的第一直觉；叫「配置项」会被问是不是另一套东西 |
| 密钥 | Secret | 已一致 |
| 有状态副本集 / 部署 / 定时任务 | StatefulSet / Deployment / CronJob | 列表页用中文，YAML 保留 kind |

**「组件」这一层不解释成"对齐"，而是解释成"差异"**：构建单元（一个镜像一个版本）与调度单元本来就不等价，这是我们相对 KubeSphere 的产品主张。

## 新增的一条待定

私有云整套交付，客户通常还会问：**平台自己怎么装、怎么升级、出问题怎么巡检**。这类「交付运维」能力在原型的 21 个页面里完全没有。是否要做，取决于评审时会不会被问到——建议先记在待定项，不占用第 0 步的篇幅。
