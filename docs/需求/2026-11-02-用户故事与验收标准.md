# 用户故事与验收标准

> 版本：v1.0　更新时间：2026-11-02 23:24
> 定位：原型评审与验收的故事基线，回答「谁要什么」与「什么算做完」。
> 产品口径以 [product-spec](../2026-10-30-product-spec.md) 为准，本文只引用规则编号（R-xx），不重复定义规则；质量缺口编号（F / E / U）引用 [quality-audit](../2026-10-30-quality-audit.md)。

## 一、使用方式

- **评审前**：按故事编号逐条点通「已实现」项，不通过的记入问题清单，不在评审现场临时解释。
- **评审中**：每条故事先讲角色与价值，再演示验收项，避免退化成功能罗列。
- **迭代时**：「未实现」项直接转为任务；完成后把状态改为「已实现」，不新建文档。
- **变更时**：先改 product-spec 的规则编号，再回写本文的验收项，禁止只改一处。
- **状态定义**：已实现 = 当前原型可验证通过；部分 = 主路径可用但有关键缺口；未实现 = 规则已定、原型未做。

## 二、角色与边界

| 角色 | 职责 | 主要故事 |
|---|---|---|
| 平台管理员 | 平台能力开关与授权：模块、角色、底座视图 | US-13、US-14、US-18 |
| 应用负责人 | 对某个应用的交付结果负责：建应用、配资源、发生产、回滚 | US-01、US-03、US-10、US-12 |
| 开发者 | 日常开发与调试：组件、依赖、配置、灰度 | US-04、US-09、US-05 |
| 运维值班 | 生产稳定性：审批、发布、告警处置、扩缩容 | US-06、US-08、US-15、US-16 |
| 只读审计 | 合规与追溯：只读查看、密钥访问留痕 | US-11 |

**原型边界**：当前原型固定以「平台管理员 张明」身份浏览，没有真实鉴权。涉及权限的验收项不按「越权操作是否被拦截」判定：界面已表达规则但未做校验的标为「部分」，完全没有对应界面或数据的标为「未实现」。这一点在评审时需主动说明，否则会被当成缺陷。

## 四、故事与验收标准

### 4.1 三层模型

#### US-01 三步创建应用

**作为** 应用负责人，**我希望** 在一个向导里同时创建应用、首个组件与首个工作负载，**以便** 业务能在一分钟内落出可继续下钻的骨架，而不必先理解集群。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-01-1 | 应用名称必填、不超过 24 个字符；重名时提示「已存在同名应用」并停在当前步骤 | 已实现 |
| AC-01-2 | 组件名与工作负载名只接受小写字母、数字与短横线；两者同名时被拦下 | 已实现 |
| AC-01-3 | 第三步展示应用、组件、工作负载的汇总，并允许取消创建组件或负载 | 已实现 |
| AC-01-4 | 创建成功后跳转 `#/apps/<id>/components`，资源树含新应用并默认选中首个组件 | 已实现 |
| AC-01-5 | 刷新页面后新应用仍在（快照落盘） | 已实现 |

#### US-02 三层资源树逐层下钻

**作为** 应用负责人，**我希望** 在应用详情按「应用 → 组件 → 工作负载」逐层展开，**以便** 定位一个实例属于哪个组件、部署在哪个位置。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-02-1 | 左侧资源树展示三级层级，缩进可辨，组件带负载数量 | 已实现 |
| AC-02-2 | 点击组件展开其负载并高亮选中项，右侧详情同步切换 | 已实现 |
| AC-02-3 | 选中工作负载时展示所属应用、组件与调度位置 | 已实现 |
| AC-02-4 | 应用下无组件时显示空态与「新建组件」引导，不出现空白表格 | 已实现 |
| AC-02-5 | 深链访问已删除的应用时显示兜底页，不白屏 | 已实现 |

#### US-03 组件改名不破坏引用

**作为** 应用负责人，**我希望** 改组件名后依赖、配置与入口都不需要重新绑定，**以便** 整理命名时不产生隐性断链。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-03-1 | 改名后依赖边仍指向该组件（按 id 解析，不按名字） | 已实现 |
| AC-03-2 | 组件作用域配置、访问入口后端仍指向改名后的组件 | 已实现 |
| AC-03-3 | 拓扑连线与组件卡片上的上下游标签同步更新 | 已实现 |
| AC-03-4 | 应用详情「校验」不报出悬空引用 | 已实现 |

#### US-04 编辑组件依赖

**作为** 开发者，**我希望** 在拓扑页直接增删组件依赖并区分同步与异步，**以便** 架构关系能被表达，而不是只存在于文档里。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-04-1 | 拓扑页可新增、删除依赖，并标注同步或异步 | 已实现 |
| AC-04-2 | 保存后连线与组件卡片的上游、下游标签同步变化 | 已实现 |
| AC-04-3 | 依赖目标组件被删除后，「校验」能列出悬空依赖 | 已实现 |

### 4.2 发布链路

#### US-05 运行流水线并观察阶段

**作为** 开发者，**我希望** 看到 8 个阶段按序推进并实时输出日志，**以便** 失败时能立刻判断卡在哪一步。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-05-1 | 阶段按「检出 → 构建 → 单测 → 推镜像 → 部署 → 回归 → 审批 → 全量」推进，当前阶段高亮 | 已实现 |
| AC-05-2 | 日志流式追加；离开页面后旧计时器停止，不出现重复输出 | 已实现 |
| AC-05-3 | 失败阶段标红并展示失败日志，可一键重跑 | 已实现 |
| AC-05-4 | 质量门禁（单测通过率、覆盖率、高危漏洞、回归用例）在运行详情可见 | 已实现 |

#### US-06 生产发布审批

**作为** 运维值班，**我希望** 生产发布在审批通过前不进入灰度，**以便** 变更可控且责任可追溯。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-06-1 | 勾选「需要人工审批」时，审批未通过不进入灰度阶段 | 已实现 |
| AC-06-2 | 审批必须填写审批人；驳回终止本次变更并记录意见 | 已实现 |
| AC-06-3 | 审批人、审批时间写入发布记录详情 | 已实现 |
| AC-06-4 | P0 应用需「应用负责人 + 运维值班」双人审批，两人都通过才放行（R-15） | 未实现 |

#### US-07 灰度推进到全量

**作为** 应用负责人，**我希望** 按 10% → 50% → 100% 观察灰度再全量，**以便** 在影响面可控时验证新版本。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-07-1 | 灰度阶段可按 10% → 50% → 100% 推进，权重在流量规则页可调整 | 已实现 |
| AC-07-2 | Mesh 关闭时「流量治理」页签锁定，发布策略退回原生滚动更新 | 部分 |
| AC-07-3 | 全量完成后发布单状态为成功，应用事件流记录新版本 | 已实现 |
| AC-07-4 | 发布记录保存访问入口快照，回滚时一并恢复 | 已实现 |

AC-07-2 说明：设计说明页已声明退回逻辑，原型未做「检测到模块关闭后自动降级」的联动。

#### US-08 回滚到上一版本

**作为** 运维值班，**我希望** 在发布记录里回滚到上一版本并看到明确的恢复范围，**以便** 故障时快速止损且不误退到更早版本。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-08-1 | 仅有上一版本（prev）的已发布记录显示「回滚」入口，其余显示占位 | 已实现 |
| AC-08-2 | 回滚弹窗列出当前版本、目标版本与入口恢复范围，确认后生成回滚记录 | 已实现 |
| AC-08-3 | 回滚同时恢复组件版本与访问入口的期望配置、已生效快照 | 已实现 |
| AC-08-4 | 回滚范围严格限制在最近一个成功版本（R-10） | 未实现 |

口径差异见 AC-08-4：R-10 写的是「只能回到最近一个成功版本」，实现是「任何有 prev 的已发布记录都可回滚」。评审前需统一：要么收紧实现，要么修订 R-10 的表述。

### 4.3 配置治理

#### US-09 新增配置并选择注入方式

**作为** 开发者，**我希望** 新增配置时选择作用域与注入方式，并被告知何时生效，**以便** 不会因为「保存了但没生效」而误判。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-09-1 | 作用域可选「全部组件」或指定组件，列表按作用域展示 | 已实现 |
| AC-09-2 | 注入方式可选环境变量或文件挂载；保存前分别提示「需重启」与「约 1 分钟热更新」 | 已实现 |
| AC-09-3 | 同一作用域内 key 重复时拦截（R-07） | 已实现 |
| AC-09-4 | 环境变量 key 只接受大写字母、数字与下划线；文件挂载以文件名为 key | 已实现 |
| AC-09-5 | 密钥在 YAML 中以 secretKeyRef 或 secret 卷引用，不写进 Deployment 明文 | 已实现 |

#### US-10 改前知影响、删前被拦截

**作为** 应用负责人，**我希望** 改配置前看到哪些负载会受影响，删除被引用项时被拦住，**以便** 不因一个共享 key 让多个服务同时起不来。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-10-1 | 编辑配置时展示生效负载数，以及被同名变量覆盖、不受影响的负载数 | 已实现 |
| AC-10-2 | 删除被引用配置时拦截，并列出前 4 个引用负载名（R-06） | 已实现 |
| AC-10-3 | 勾选「强制删除」后可继续，事件流记录影响负载数量 | 已实现 |
| AC-10-4 | 无引用的配置显示「可以安全删除」，不出现无意义拦截 | 已实现 |

#### US-11 密钥查看受控并留痕

**作为** 只读审计，**我希望** 密钥明文默认不可见、查看动作可追溯，**以便** 合规检查时能回答「谁在什么时候看过」。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-11-1 | 密钥值默认隐藏，列表与详情不直接展示明文 | 已实现 |
| AC-11-2 | 仅平台管理员与应用负责人可查看明文，其他角色无入口（R-08） | 未实现 |
| AC-11-3 | 每次查看写入审计日志：操作人、时间、密钥标识（F7） | 未实现 |
| AC-11-4 | YAML 视图与导出内容中始终不出现明文 | 已实现 |

#### US-12 配置变更走独立发布单

**作为** 应用负责人，**我希望** 配置变更也生成可审批、可回滚的发布单，**以便** 配置改错时能退回去，而不是只能改回来。

| 编号 | 验收标准 | 状态 |
|---|---|---|
| AC-12-1 | 保存配置时生成独立发布单，含变更前后快照（R-16） | 未实现 |
| AC-12-2 | 配置发布单可审批，审批前不生效 | 未实现 |
| AC-12-3 | 配置发布单可回滚，回滚恢复快照中的配置值 | 未实现 |
| AC-12-4 | 配置变更在应用事件流中留痕 | 部分 |
